# 사이트 구조 사양 (REV 1)

> **영구 규격.** 프로젝트가 바뀌어도 이 문서는 그대로 적용된다. 개선 시 REV를 올린다.
> 작업지시서에 이 내용을 복사하지 말고 조항 번호로 참조한다.
>
> **근거 표기**: 각 조항의 근거는 관측 출처와 시점을 함께 남긴다. "그렇게들 한다"는 근거가 아니다.

---

## § 1. 되돌리기 어려운 결정 (가장 먼저 확정할 것)

**1.1~1.5는 나중에 고치면 301 리다이렉트와 재색인이 필요하다.** 빌드 전에 확정한다.

| 조항 | 규격 | 근거 |
|---|---|---|
| **1.1** | **호스트는 하나.** www 또는 non-www 중 하나로 301 통일. canonical·og:url·sitemap·robots·내부링크가 전부 같은 호스트를 쓴다 | 두 호스트가 모두 200을 반환하면 링크 신호가 분산되고, IndexNow는 host 불일치 시 422로 거절 (2026-09 실측) |
| **1.2** | **URL은 루트 직하 평면 구조.** 카테고리 접두어를 넣지 않는다. 계층은 브레드크럼과 내부링크로 표현 | 화환 시장 상위 6곳 공통 (2026-09-02 관측) |
| **1.3** | **한글 URL은 붙여쓰기, 하이픈 금지**<br>`/밀양시민장례식장화환/` ○ `/밀양시민-장례식장/` ✕ | 검색어 완전일치 신호. 상위 3곳이 공백(%20) 사용, 하이픈 사용처 0곳 |
| **1.4** | **대상 1개 = 페이지 1장.** 키워드 변형으로 URL을 늘리지 않는다. 유사어는 한 문서의 title·본문·FAQ로 커버 | 시설당 20개 URL을 만든 곳, 폴더를 4벌 복제한 곳 모두 중복 부채를 떠안음 |
| **1.5** | **canonical은 자기 참조. 예외 없음** | 타 도메인을 가리켜 순위 자산을 넘긴 사례 3곳 관측. 그중 하나는 **매물로 나온 도메인**을 가리키고 있었음 |
| **1.6** | **4계층 사일로** — 홈 → 대분류 → 중분류 → 개별. 허브도 각각 검색어를 노린다 | 클릭 깊이 3 이내 유지 |
| **1.7** | **고아 페이지 0.** 브레드크럼(상향) + 형제 링크 12개 내외(횡) + 허브 전체 목록(하향) | 사이트맵은 발견 수단일 뿐 권위 전달 통로가 아니다. 내부링크 없는 페이지는 재크롤링 우선순위에서 밀린다 |
| **1.8** | **사이트맵에 실제 페이지 전부.** robots.txt에 선언. 위장 사이트맵 금지 | 실제 페이지 수천 장인데 사이트맵에 15개만 넣은 사례 관측 |
| **1.9** | **버티컬은 도메인 또는 최상위 폴더로 분리.** 성격이 다른 사업을 한 사이트에 섞지 않는다 | |
| **1.10** | **정적 생성 + CDN. 외부 스크립트 0에 수렴** | 상위권 전부 외부 요청 0~1건 |

## § 2. 개별 페이지 구조

**블록의 순서가 규격이다.** 01~04가 검색결과 노출 구간, 05 이하가 체류·전환 구간.

```
01  브레드크럼                       사일로 상향 연결
02  H1 — 대상명 + 핵심 키워드          완전일치. title보다 짧게
03  첫 문단 — 핵심 사실 요약           스니펫이 잡히는 구간
04  1차 CTA                          스크롤 없이 보이는 위치
05  고유 데이터 블록                   ★ 이 페이지에만 있는 정보  ← 경계선
06  가격·사양 등 정량 정보             페이지 안에 노출
07  절차 안내
08  보조 정보
09  FAQ 4~6                          질문 문장에 대상명 포함
10  형제 링크 + 상위 허브 링크          고아 방지·사일로 순환
11  2차 CTA
```

### 2.1 ★ 05번 블록이 이 사양의 경계선이다

**이 블록이 비면 나머지를 아무리 채워도 이름만 치환된 껍데기이고, 그 순간 프로그래매틱 SEO가 아니라 도어웨이가 된다.**

이것이 대량 생성 페이지의 **합격/불합격을 가르는 유일한 검사 기준**이다. 추상적인 "가치를 더하라"가 아니라 코드로 검사할 수 있는 규칙으로 쓴다.

**발행 조건을 코드에 박을 것**
- 05번 블록에 채울 고유 데이터가 없으면 **페이지를 생성하지 않거나 `noindex`** 처리한다
- 어떤 필드가 몇 개 이상 있어야 발행하는지 프로젝트별로 정하고 작업지시서에 명시한다
- 예: "주소·연락처·정량 지표 중 2개 이상 존재" / "관측 데이터 2회 이상 누적"

### 2.2 ★ 문장 다양화는 데이터에서 나와야 한다

**상용 문구 pool에서 무작위로 골라 조합하는 방식(스핀)을 쓰지 않는다.**

같은 뜻의 문장을 동의어로 돌려막으면 겉모습만 달라지고 **정보량은 그대로**다. 이것이 정확히 스팸 판정이 겨냥하는 패턴이며, 사람이 읽어도 어색하다.

```
✕  "{지역}에서 가장 신뢰받는" / "{지역} 최고의" / "{지역} 믿을 수 있는"  ← pool 랜덤
○  "{지역} {업종} {N}곳 중 {순위}위. 평균 {값} 대비 {차이}"              ← 데이터가 문장을 만든다
```

**허용되는 템플릿 사용**
- 문장 **틀**은 재사용해도 된다. 그 틀에 들어가는 **값이 페이지마다 실제로 다르면** 된다
- 값이 전 페이지 동일한 문단(회사 소개·배송 안내·약관성 문구)은 있어도 되지만, **그것만으로 페이지를 구성하면 안 된다**

**사람이 써야 하는 부분**
- 지역 특징, 랜드마크, 실제 사례처럼 **데이터로 자동 생성할 수 없는 서술**은 페이지마다 사람이 쓴다
- 이걸 감당할 수 없으면 **페이지 수를 줄인다.** 수를 채우려고 문구를 지어내는 순간 사이트 전체가 위험해진다

### 2.3 메타 공식

```
title        {대상명} {핵심어} {행동어} · {보조어} | {브랜드}
H1           {대상명} {핵심어}                     ← title보다 짧게
description  {대상명}의 핵심 사실 + 정량 정보 + 지역. 공백 포함 150~200자
canonical    자기 자신 (percent-encoding 그대로)
og:          title / description / image 1200×630 / url / locale=ko_KR
```

## § 3. 허브 페이지

허브는 목록 페이지가 아니라 **그 자체가 상위 검색어를 노리는 페이지**다.

```
브레드크럼
H1        {지역} {업종} {핵심어}
첫 문단     {지역} {업종} {N}곳 · 정량 요약    ← 숫자를 문장에 넣는다
CTA
목록        그 범위의 전 대상
정량 정보    개별 페이지와 동일 기준
인접 지역    같은 상위 범주의 형제 12개
상위 허브    전체 보기
```

**숫자를 문장에 넣는 것**이 단순 목록 페이지와 갈리는 지점이다.

## § 4. 이미지 자산 (빌드 전에 준비)

같은 이미지가 수백~수천 페이지에 반복 노출되는 구조이므로 **빌드 전에** 준비한다. 준비 없이 시작하면 페이지 전부가 텍스트만 남는다.

| 항목 | 규격 | 이유 |
|---|---|---|
| 대표·상품 이미지 | 사전 준비 필수 | 검색결과 썸네일 카드 노출에 영향 |
| 파일 크기 | 표시 크기에 맞게 리사이즈 + JPEG quality 75~80 | 원본 그대로 쓰면 페이지당 수백 KB가 누적 |
| 배치 | **외부 공유 파일**로 두고 여러 페이지에서 재사용 (`/assets/…`) | 브라우저 캐싱 — 첫 페이지에서만 받고 이후 재다운로드 0 |
| **base64 인라인** | **금지**(반복 노출되는 이미지의 경우) | 페이지마다 중복 전송되어 캐싱 이점이 사라진다. 전송량이 외부파일 방식보다 수십~수백 배 커짐. 그 페이지 전용의 아주 작은 아이콘 1회성 용도만 예외 |
| **이미지 슬라이스** | **금지** | 여러 장을 이어붙여 하나처럼 보이게 하면 검색결과 썸네일에서 조각만 잘려 나온다 |
| **텍스트 박힌 이미지** | og:image 용도는 무방, **본문 대체 금지** | 이미지 속 텍스트는 크롤러·스크린리더가 실제 텍스트만큼 신뢰하지 않는다. 가격·상품명 등 핵심 정보는 **반드시 HTML 텍스트로도 존재**해야 한다 |
| alt 텍스트 | 전 이미지 필수 | 접근성 + 이미지 검색 |
| `loading="lazy"` | 첫 화면 밖 이미지에 적용 | |
| favicon / og:image | 빌드 전 확보, 공통 레이아웃에 기본 포함 | 없으면 소셜 공유·탭에서 브랜드 인식 저하 |

## § 5. 성능 예산

| 항목 | 기준 | 비고 |
|---|---|---|
| 페이지 용량(HTML) | 10KB 이하 | 대량 정적 페이지 기준 |
| 외부 요청 | 0~1건 | 폰트·분석 스크립트 포함해서 센다 |
| 외부 스크립트 | 0에 수렴 | 광고·채팅 위젯이 성능 예산을 통째로 먹는다 |
| 본문 분량 | 시장 상위권을 실측해 정한다 | 절대 기준 없음. **경쟁 상위 페이지를 직접 재서** 목표를 잡을 것 |

분량 목표를 못 채우면 **문장을 늘리기 전에 데이터를 먼저 보강한다**(§2.2).

## § 6. 금지 사항

| 금지 | 대가 |
|---|---|
| 하이픈 슬러그 (한글 URL) | 검색어 완전일치 신호 손실 |
| www / non-www 방치 | 링크 신호 분산 · IndexNow 422 |
| canonical을 타 도메인으로 지정 | 순위 자산을 남에게 넘김 |
| 위장 사이트맵 | 수동 색인 투입에 전적으로 의존하게 됨 |
| 키워드 변형 URL 증식 | 도메인 단위 중복 부채 |
| 미래 날짜 `lastmod` | 사이트맵 신뢰도 하락 |
| 고유 데이터 없는 얇은 페이지 대량 발행 | 사이트 전체 평가 하락 (§2.1) |
| 문구 pool 랜덤 조합 | 스팸 패턴. 정보량 증가 없음 (§2.2) |
| 가격을 외부 몰에만 노출 | 가격 검색 의도를 통째로 넘김 |
| 경쟁사 문장 복사 | 공공데이터 **필드**는 무방하나 **문장은 저작물** |
| 데이터 없는 필드를 추정값으로 채우기 | 사실이 아닌 정보가 대량 유포됨 |

## § 7. 적용 우선순위 (효과 ÷ 비용)

1. **호스트 통일(1.1)** — 설정 1개. 안 하면 이후 색인 작업이 절반으로 샌다
2. **커버리지 채우기** — 없는 페이지는 순위가 없다. 목표 모수를 먼저 정한다
3. **사이트맵 정합성(1.8)·lastmod 정리** — 대량 색인 요청은 여기까지 끝난 뒤
4. **슬러그 교정(1.3)** — 301 필요. 소규모로 검증 후 전체 적용
5. **페이지 블록 순서 정비(§2)**
6. **버티컬 확장(1.9)** — 하나로 검증된 뒤

## § 8. 커버리지 기준선 잡는 법

대량 페이지 생성 프로젝트는 **"몇 개가 있어야 정상인지"를 먼저 안 다음** 데이터를 검증한다.

- 공공데이터·업계 통계·경쟁사가 공개한 수치 중 하나를 기준선으로 삼는다
- 변환 후 **분류별 개수를 기준선과 대조**한다
- **기준선보다 20% 이상 적으면 원본 데이터 누락을 의심하고 보고**한다

기준선 없이 만들면 "데이터에 있는 만큼"만 만들고 빠진 걸 영영 모른다.
